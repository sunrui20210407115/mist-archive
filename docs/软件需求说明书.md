## 一、项目目标

开发一个以“调查校园档案盒失踪案”为主线、可完整游玩的 HarmonyOS 应用。玩家从接案开始，在三个场景中探索、获取线索、触发人物对话，线索与选择会真实改变后续可执行的选项；条件满足后可进入终局判断，并按条件进入两个不同结局。应用中途被结束后重新打开，能恢复到上次进度。

核心约束：

1. 不是静态页面拼接，每个选择都要经过规则判定并改变状态。
2. 线索是硬门槛：缺少线索时对应选项不可用，而不是用文字提示敷衍。
3. 状态可持久化、可重开。

## 四、数据模型

### 4.1 运行状态 GameState

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| stage | number | 0 接案、1 调查中、2 可终局、3 已结案 |
| sceneId | SceneId | 当前场景 |
| currentNodeId | string | 当前事件节点 |
| clues | string[] | 已获得线索 id 集合，去重 |
| flags | Record<string, boolean> | 剧情标记，如 flag_guard_trust、flag_tape_played、flag_motive |
| visited | string[] | 已访问节点，用于界面回显 |
| endingId | string | 结算后的结局 id |
| updatedAt | number | 最后更新时间戳 |

### 4.2 线索 Clue

`id`、`name`、`sceneId`、`detail`。6 条线索：借阅登记本残页、值班台备用钥匙、社团排练录音磁带、门禁记录打印件、匿名纸条、值夜表。

### 4.3 事件节点 EventNode 与选择 Choice

节点：`id`、`sceneId`、`title`、`body`、`req?`、`choices[]`。
选择：`id`、`label`、`req?`（条件）、`effects?`（效果）、`nextNodeId?`、`hint?`（条件不足时的提示）。

条件 Requirement：`clues[]`（需全部持有）、`anyFlags[]`（任一成立）、`noneFlags[]`（均不成立）、`minStage`。
效果 Effects：`addClues[]`、`setFlags[]`、`clearFlags[]`、`advanceStage`。

### 4.4 结局 EndingDef

`id`、`title`、`subtitle`、`body`、`req`。结局 A 要求 4 条物证线索 + 动机标记 + 阶段 2；结局 B 无条件，作为兜底。

### 4.5 存档 SavePayload 与日志 LogEntry

存档：`version`（当前为 2）+ `state`。
日志：`nodeId`、`choiceId`、`clueAdded`、`createdAt`，落库为 `event_log` 表（自增主键）。

## 五、接口定义

| 接口 | 签名 | 说明 |
| --- | --- | --- |
| RuleEngine.satisfies | `(state: GameState, req?: Requirement): boolean` | 条件判定，空条件恒真 |
| RuleEngine.applyEffects | `(state: GameState, effects?: Effects): GameState` | 返回新状态，线索去重、标记置位、阶段只增不减 |
| RuleEngine.evaluateStage | `(state: GameState): number` | 依据线索数与关键标记推进阶段 |
| RuleEngine.applyChoice | `(state, nodeId, choiceId): AdvanceResult` | 执行一次选择，返回 `{ok, state, message, addedClues}` |
| RuleEngine.resolveEnding | `(state: GameState): EndingDef` | 按顺序匹配结局条件 |
| SaveService.init | `(context: common.UIAbilityContext): Promise<void>` | 打开 Preferences 实例 |
| SaveService.save | `(state: GameState): Promise<void>` | 写入快照并 flush |
| SaveService.load | `(): Promise<GameState \| null>` | 读取、校验版本、规范化；损坏时清档返回 null |
| SaveService.clear | `(): Promise<void>` | 删除存档键 |
| SaveService.normalize | `(source?: GameState): GameState \| null` | 字段容错与非法线索过滤 |
| LogRepo.init / append / recent / count | 见源码 | RDB 初始化、写入、倒序查询、计数 |
| GameStore.restore / newCase / restart / choose / submitFinale | 见源码 | 会话动作，内部触发持久化与日志 |

### 模块交互

`Index` 持有 `GameStore`，各视图以 `@ObjectLink` 订阅；视图只调用 `GameStore` 的动作，不直接读写存储。`GameStore` 调用 `RuleEngine` 计算新状态，调用 `SaveService` 落盘、`LogRepo` 写日志。`StoryData` 与 `GameTypes` 为纯数据与类型，被规则引擎与视图共用。

## 六、测试方案

用例覆盖正常、边界、异常三类，详见 `docs/测试记录.md`。测试对象以 `RuleEngine` 的条件判定、效果应用、阶段推进、结局裁决为主，辅以 `SaveService.normalize` 的容错行为。

## 七、验收方式

1. 编译：`assembleHap` 构建成功并产出 HAP。
2. 玩法闭环：接案 → 收集线索 → 条件拦截可见 → 阶段到 2 → 终局 → 结局 A/B 均可复现。
3. 持久化：游玩中途杀进程，重新打开后阶段、线索、当前节点与上次一致。
4. 重开：点击重开后线索归零、阶段回到调查中。
5. 测试：自动化用例全部通过，覆盖正常、边界、异常。
6. 代码与提交历史：仓库内可查到本人账号的分模块提交记录。
